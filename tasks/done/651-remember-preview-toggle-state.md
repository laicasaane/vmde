## Current behaviour (from source)

Preview is Vditor's overlay, switched by the toolbar's Preview button. VMDE opens a document in Preview only when the host resolves the open mode to `preview` (`platform/default-mode.ts`: the first matching `vmde.editor.defaultModeByGlob` rule, else `vmde.editor.defaultMode`); the webview then clicks the button (`chrome/open-preview.ts`). Documents over 700,000 characters stream into an edit mode and never open in Preview. Turning Preview on or off by hand is not stored: the next document opens in its resolved or remembered edit mode.

## Requirements

1. **Preview is the fourth mode, with its own toggle.** Preview sits beside the three edit modes (WYSIWYG, Instant Rendering, Split) but is switched by the Preview toggle, not by the Edit Mode menu. Whether Preview is on is kept across VS Code sessions and is shared by every file.
2. **Preview on.** Every document opened after Preview is turned on opens in Preview, unless a path rule (`vmde.editor.defaultModeByGlob`) or an explicit `vmde.editor.defaultMode` value (`ir`, `wysiwyg`, `sv` or `preview`) chooses its mode. Path rules and the setting keep supporting `preview`.
3. **Preview off.** The editor returns to the stored edit mode (WYSIWYG, Instant Rendering or Split), and documents opened after that open in that edit mode.
4. **Only the toggled editor changes.** Other open editors keep their state until they are reopened.
5. **Large documents.** They open in Preview too. Until [Task 643](../643-preview-mode-streaming-performance.md) streams them into Preview, a document over the streaming threshold (700,000 characters) opens in Preview after it has finished streaming into its edit mode.
6. **No document effect.** Toggling or opening in Preview changes no document text, dirty state, Undo history, caret or selection.
7. **Storage.** The state is a profile-local `globalState` value, not synced across machines, like the toolbar collapse state.

## Open design points (settled in Part 1)

- How the stored edit mode (`vmde.options` `mode`, synced) and the new Preview value combine at open, and which one `defaultMode: "remember"` reads.
- Where the rule lives: host-side in `resolveDefaultMode` (which knows the path rules) or in the webview; how the streaming exception reaches it.
- How Preview combines with Split, which has its own preview pane (Preview over Split today opens the overlay over the Split layout).
- Which toggles store the value: the toolbar button, the `vmde.switchTo*` commands, the status-bar mode control, and opening in Preview because of a path rule or the setting (proposed: only user toggles store; rule-driven opens do not).

## Scope

- In: the stored Preview state, the open rule, the streaming interim behaviour, `init` and first-paint delivery.
- Out: the toolbar placement and icon of the Preview control (Task 642), Preview rendering and streaming (Task 643).

### Verified facts

- Preview is Vditor's overlay over the current edit mode, not a mode. - `chrome/open-preview.ts:11-18` clicks that same button (no-op when it already has `vditor-menu--current`). It is called once, from `boot/vditor-init.ts:573`, only on the non-streaming path and only when `msg.options.defaultMode === 'preview'`.

### Decisions

1. **Combination of stored edit mode and Preview.** Two independent values: edit mode stays in `vmde.options` `mode` (synced, unchanged); Preview on/off is a new profile-local `globalState` boolean. Reopening applies the stored edit mode and then, if Preview is remembered on, the Preview overlay on top (Preview over Split works because `Preview.ts` handles `sv`). Preview off removes only the overlay, so the editor returns to the stored edit mode. `defaultMode: "remember"` therefore reads both values; the setting value `remember` and an absent value are the same case (`resolveDefaultMode` returns `undefined`).
2. **Precedence.** `resolveDefaultMode` is unchanged and still decides first. The remembered Preview applies only when it returns `undefined` (no matching path rule, setting `remember`). An explicit `ir`, `wysiwyg` or `sv` value, or any path rule, wins whatever the toggle holds (and does not clear it). `preview` from a rule or the setting keeps its Task 282 behaviour exactly (maps to IR, small documents only).
3. **Where the rule lives: host.** New pure function `opensInRememberedPreview(resolved: OpenMode | undefined, previewOn: boolean): boolean` in `platform/default-mode.ts` (returns `resolved === undefined && previewOn`). `buildInitOptions` calls it with `collectConfigOptions(uri).defaultMode` and `readPreviewOn(globalState)` and adds `openInPreview: true` to the options only when true (omitted otherwise), after the saved-options spread. Both the `init` post and the inline payload get it with no other change. The webview does no precedence logic.
4. **Streaming exception.** The webview opens the remembered Preview after the stream completes: in the streaming branch's `onDone`, after `finishHelpers()`, call `openInPreview()` when `msg.options?.openInPreview === true` (never on the failure path, where the restored document stays editable). The non-streaming path opens it where line 573 does today (`defaultMode === 'preview'` or the remembered flag). Only the remembered case opens after streaming; a `preview` rule on a streamed document keeps opening editable (282 behaviour), which Task 643 can revisit. When Task 643 streams into Preview, the `onDone` call is the only line to remove.
5. **Split.** Preview over Split is kept as the existing overlay over the Split layout; no special case. Stored mode `sv` plus Preview on opens Split then the overlay; Preview off restores the Split source and preview panes.
6. **Which actions store.** Only a user click on the toolbar Preview button (mouse, or keyboard activation, which also arrives as a click). Not stored: any open driven by the stored value, a path rule or the setting (`openInPreview()` runs inside a guard that marks its own click as programmatic), re-init, the `vmde.switchTo*` commands, and the status-bar control (neither is a Preview control). The listener posts the state read from the button class after Vditor's own handler has run (it is bound later, so it runs second), and posts nothing when the click left the class unchanged (a disabled button).
7. **Other open editors: unchanged** (requirement 4). No broadcast, no host-to-webview message, no registry walk; the value is read at editor open only. A webview re-init inside a running editor keeps that editor's own Preview state: capture `previewShowing()` before `vditor.destroy()` and, for the remembered case only, reopen Preview iff it was showing (an explicit `preview` rule behaves as today). Test: a re-init after another editor toggled does not change this editor.
8. **Alignment with Task 650.** Recommend 650 uses the same rule, so both tasks share one storage pattern: write on user action, read at editor open, open editors keep their state until reopened, no fan-out. Reason: the Preview toggle must not move other editors (Owner requirement), one rule is easier to explain, and it avoids the registry broadcast and its disposed-panel handling. 650 can only differ if it wants the width to follow live resizes; I see no reason to. The two tasks edit the same four host files (`state-keys.ts`, `editor-session.ts`, `protocol.ts`, `webview-message-shape.ts`), so the second to land rebases on the first; keep each addition in its own block to make that mechanical.

### State key, messages, shapes

- Key: `KeyPreviewOn = 'vmde.previewOn'` in `platform/state-keys.ts`; `readPreviewOn(store: { get(key: string): unknown }): boolean` returns `store.get(KeyPreviewOn) === true` (absent, null, string, number, object all mean off). Profile-local: not added to `setKeysForSync`.
- Webview to host: `{ command: 'save-preview-state'; on: boolean }`. Shape table entry `'save-preview-state': [['on', 'boolean']]` (a non-boolean is dropped before the handler). Handler `onSavePreviewState` writes `globalState.update(KeyPreviewOn, message.on === true)`, awaits nothing else, posts nothing.
- Host to webview: no new message. New optional field `openInPreview?: boolean` on `InitOptions` in `shared/protocol.ts` (next to `defaultMode`), meaning "Preview was left on and no explicit mode applies; leave the edit mode alone".
