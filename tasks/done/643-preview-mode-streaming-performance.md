# Task 643 — Preview mode: stream large documents and render faster than the edit modes

**Status:** implemented and verified 2026-11-01; ready to close (see the last Progress entry for the caveats).
**Origin:** Project Owner feature request.
**Severity:** feature (medium risk; replaces how Preview renders).
**Tech stack:** TypeScript webview (`media-src/src/chrome/open-preview.ts`, `editing/preview-state.ts`, `editing/preview-morph.ts`, `diagrams/stream-render.ts`, `util/stream-chunk.ts`, `boot/vditor-init.ts`, `boot/finish-init.ts`), Lute (`Md2HTML`), diagram renderers, Vitest, Chromium, real VS Code.
**Related:** [Task 642](642-toolbar-layout-follow-ups.md) (Preview becomes the fourth mode with its own remembered toggle), [Task 641](641-open-to-ready-one-second.md) (open-to-ready time; its deferred "render what is on screen first" item).

## Problem

Preview is Vditor's overlay, not a mode VMDE renders. VMDE turns it on by clicking Vditor's Preview button (`chrome/open-preview.ts`). Vditor then reads the whole document back out of the edit view, converts it to HTML in one `Md2HTML` call, and runs every diagram, math and code renderer.

This has three costs:

- **Preview waits for an edit mode.** It reads its Markdown from the edit view, so the edit view must be built first, including the edit-only work that Preview does not need.
- **No streaming.** The edit modes stream documents over 700,000 characters in about 4 KB chunks (`diagrams/stream-render.ts`, `STREAM_MIN_CHARS`). Preview has no streaming path, so a large document is one long render. For that reason a large document never opens in Preview today (`boot/vditor-init.ts`).
- **Slower than it needs to be.** Preview is read-only, yet it pays for the edit modes' startup: the editable DOM, Undo history, the source index, caret and selection handling, and the edit-surface observers.

## Requirements

1. **Preview is its own mode.** Preview renders the document itself instead of driving Vditor's overlay. It renders from the document text the host sends, not from an edit view, and does not build an edit view first.
2. **Streaming.** Documents over the streaming threshold stream into Preview in chunks, as the edit modes do. Content appears progressively, and no single render step blocks the editor long enough to be noticed. Links and footnotes that point across chunks render exactly as in a one-pass render (reuse the cross-chunk definition handling in `stream-chunk.ts`).
3. **Faster than the edit modes.** For the same document, Preview reaches visible content and finishes rendering faster than IR, WYSIWYG and Split, because it skips edit-only work: no editable DOM, no Undo history, no source index, no caret or selection tracking, no edit-surface observers.
4. **Render what is on screen first.** Diagrams, math and other heavy blocks render when they are on or near the screen, not all at open.
5. **Same output.** Preview looks the same as today's Preview for the same document and settings: content theme, code highlighting, diagram palettes, callouts, Details, wiki links, anchors, images and remote-content rules.
6. **Same Preview features.** Everything Preview offers today keeps working: interactive task-list checkboxes (one exact source edit, one Undo step), link and wiki-link navigation, heading anchors, the outline and its highlighting, reading position when switching to and from an edit mode, copy, diagram controls, and the read-only toolbar state.
7. **Find works in Preview; Replace does not.** Find opens in Preview, searches the rendered document and highlights and scrolls to matches. The Replace row and its actions are unavailable in Preview, and Replace keys do nothing there.
8. **Mode switching.** Switching between Preview and an edit mode keeps the reading position and leaves the document, dirty state and Undo history unchanged. The edit view is built only when the user switches to an edit mode.
9. **Split's preview pane.** Part 1 decides whether Split's preview pane uses the same renderer and streaming.

## Open design points (settled in Part 1)

All points below are settled in "Part 1 handoff (2026-11-01)". Where the handoff differs from the provisional decision recorded here (render target, reading-position anchoring), the handoff wins.

- Where the renderer lives (a new module beside `diagrams/stream-render.ts`) and how much of Vditor's `Preview.render` post-processing it reuses or replaces.
- How Preview gets the document text before an edit view exists (the `init` message and the incremental seed), and how it follows host edits while open (external changes, checkbox edits).
- How the existing current-render reuse (`editing/preview-state.ts`) and preview morphing (`editing/preview-morph.ts`) fit the new renderer.
- The streaming threshold and chunk size for Preview, which may differ from the edit modes because Preview has no editable DOM.
- How Find, the outline and reading-position anchoring work without Vditor's Preview pane. **Provisional decision (2026-11-01, reversible; Part 1 confirms or replaces it):** a Preview-owned surface adapter that works from the rendered Preview DOM, not from the Markdown source.
  - **Find.** A Preview search source walks the Preview container's rendered text nodes, skipping diagram SVG, KaTeX internals, copy buttons and hidden nodes. It matches the query (literal, case, whole word) against that text and builds DOM ranges directly. The existing overlay highlight painter and the Find widget are reused. In Preview the Replace row is hidden and Replace actions do nothing. Matches update as streamed chunks arrive. Text inside heavy blocks that have not rendered yet is not searchable.
  - **Outline.** The Preview renderer gives headings ids with today's slug rules. `nav/outline.ts` resolves headings in the new Preview container instead of Vditor's `preview.previewElement`. Click-to-flash already resolves headings by id, so it is unchanged.
  - **Reading position.** The renderer stamps each top-level block with its source start line, derived from chunk offsets and Lute block boundaries. A mode switch maps that line to the matching block on the other side and reuses the fractional within-block interpolation of `nav/preview-scroll-preserve.ts`. Line keys avoid in-order block pairing, which fails where blocks render to nothing (link reference definitions).
  - **Rejected.** (a) Reusing the exact-source Find path (`find-source.ts`, `find-map.ts`, `find-align.ts`): it needs a source index and per-block Lute serialization, which requirement 3 excludes, and it searches source bytes, not the rendered document (requirement 7). (b) Rendering into Vditor's `preview.previewElement` so `outline.ts` and `preview-scroll-preserve.ts` stay unchanged: it needs Vditor initialized before Preview shows content, which requirement 1 excludes.
  - **Evidence.** Today `activeModeElement` (`util/source-map.ts`) returns the edit mode's element, so Find in Vditor's Preview overlay targets the hidden edit pane (code reading, not run). Selected by a recorded decision check (probability 0.87); all three checked requirements were supported (no source index or edit DOM in Preview, matches the rendered text, reading position survives non-1:1 blocks); both alternatives were contradicted on at least two.
  - **Open for Part 1.** Whether Lute `Md2HTML` can report block source lines or VMDE must compute them per chunk. Whether a match may span a rendered block boundary.
- Measurable targets for requirement 3 (for example, open-to-visible and open-to-complete times relative to IR on the Task 641 fixtures), proposed in Part 1 for the Owner.

Design only: no product or test file changed, nothing built or run except read-only Lute probes in Node (`tmp/643/`, untracked). Every path and line below was read at `dev` `3dd38c6d`. Part 2 starts after Task 644 is on `dev`; each Part 2 step re-reads the files it owns first.

### Problem and root cause (inference until measured in Part 2)

- Preview today is Vditor's overlay. The toolbar handler (`vditor/src/ts/toolbar/Preview.ts`, patched by Task 530 to call `window.__vmdeEnterPreview`) calls `Preview.render`, which reads the exact source through `__vmdePreviewSnapshot`, masks comments, raw headings and SVG data images, runs one `Md2HTML`, morphs the pane (`editing/preview-morph.ts`) and then runs every renderer in `afterRender` over the whole pane.
- Inference: Preview is slow to open because it can only open after the edit view is built. Task 641 measured the edit build for 150 KB at about 1.4 s (Md2VditorIRDOM plus wrapper passes), plus `runFinishInit` work on the edit DOM and the host incremental seed (966 ms). The overlay itself adds one monolithic `Md2HTML`: measured in Node on the vendored Lute, 294 ms for 150 KB and 1,055 ms for 700 KB, and all heavy renderers at once.
- Large documents never open in Preview (`boot/vditor-init.ts:597-605`), because a one-pass Preview render of a streamed document is the freeze streaming avoids.

### Settled design

1. **Render target.** Opening in Preview still constructs the Vditor shell, with an empty value, exactly as the edit streaming path does (`vditor-init.ts` `willStream`): toolbar, Lute, outline, and an empty edit element. The document's edit DOM (Md2VditorIRDOM/Md2VditorDOM/SV render), Undo base, source index and host incremental seed are not built. A new VMDE renderer renders the host text into Vditor's existing `preview.previewElement`, so every Preview feature already bound to that element or to `#app` keeps working unchanged: callouts, bare URLs, code refs, colour literals, HTML comments, SVG data images (`boot/finish-init.ts:471-544`), task checkboxes (`editing/preview-task-checkboxes.ts:168`), the outline (`vditor/src/ts/outline/index.ts`, `nav/outline.ts:175-179`), outline viewport sync, section indent, the custom-diagram observer on `#app`, scroll preservation, copy, and Task 644's rendered-id lookup root (`inner.preview.element` when shown). This replaces the provisional "own container" design: its rejection of rendering into `previewElement` assumed Vditor initialization means building an edit view, which the streaming path already shows is not so. *Provisional decision (2026-11-01), reversible.* Selected by a recorded decision check (probability 1.00; all three checked requirements supported; the own-container and line-stamp alternatives were contradicted on reading position without a new source-position mechanism).
2. **Routing.** One new anchor-asserted Vditor source patch, `patchPreviewFullRoute` in `media-src/esbuild-shared.mjs` (chained into the existing `preview/index.ts` transform), inserts at the top of `Preview.render`, after its `display === "none"` early return: `if ((window as any).__vmdeRenderFullPreview?.(vditor, value, vmdeImmediate)) { return; }`. The hook returns `true` only for full Preview: the preview element is shown and the current edit pane is hidden (`sv`: `vditor.sv.element.style.display === 'none'`; `ir`/`wysiwyg`: `vditor[mode].element.parentElement.style.display === 'none'`). Split's right pane returns `false` and keeps Vditor's path byte for byte. Every caller of `Preview.render` (the toolbar, `refreshVisiblePreviewAfterHostUpdate`, `applyPreviewReflowSetting`, theme re-renders) is routed by this one hook. `__vmdeEnterPreview` (reuse check) is unchanged.
3. **Split's preview pane (requirement 9).** Keeps Vditor's `Preview.render` and the Task 187 morph; only full Preview uses the new renderer. Both share the same Markdown masks and soft-break rule, so their HTML for the same text is equal; real-VS-Code output tests use the Split pane as the independent reference render. *Provisional decision (2026-11-01), reversible.* Selected by a recorded decision check (probability 1.00; the shared-renderer alternative was contradicted on unchanged Split typing refresh).
4. **Source text.** The renderer renders the exact source: on entry from an edit mode, `window.__vmdePreviewSnapshot()` (the Task 607 exact snapshot, `installPreviewState`); in a Preview-first open, the `init` (or inline init) `msg.content`, which is also EditSync's `initialMarkdown`. `__vmdePreviewMarkdown` (hard-break recovery from the edit DOM) is not used: the exact text already carries authored hard breaks. Masks are applied to the whole document once, before chunking: `maskCommentsForPreview` (`editing/html-comment.ts`), then `markRawHeadingsForPreview` (`nav/preview-raw-headings.ts`), then `maskSvgDataImagesForPreview` (`editing/svg-data-image-adapter.ts`), the same order as the Task 83/367/660 patch chain. Each `Md2HTML` call flips `SetSoftBreak2HardBreak(!window.__vmdeReflowPreview)` and restores `true` in `finally`, as `vmdePreviewMd2HTML` does.
5. **Chunking and cross-chunk definitions.** `chunkize` (`util/stream-chunk.ts`) gains an optional size parameter (`chunkize(md, size = STREAM_CHUNK_CHARS)`, `avoidListSplit` uses it); edit-mode callers are unchanged. Per chunk, the renderer feeds Lute `chunk + "\n\n" + externalDefsFor(chunk, defMap).text`. Measured facts (Node probe, vendored Lute): `Md2HTML` renders link reference definitions to nothing, so injected link definitions need no stripping; footnotes are numbered by definition order in the fed text (not reference order), unused definitions are listed, every definition is collected into one trailing `<div class="footnotes-defs-div">`, a repeated reference gets `id="footnotes-ref-N:k"`, and the definition carries one back-link per occurrence. So per chunk the renderer removes the chunk's `.footnotes-defs-div` and rewrites each `sup.footnotes-ref`: local number n maps to the label at position n of the chunk's local footnote order (the chunk's own definitions in line order, then the injected ones in injection order), the label maps to its global number (its position in the whole document's footnote definition order), and a per-label occurrence counter gives `id` `footnotes-ref-N` for the first and `footnotes-ref-N:k` after; `href` becomes `#footnotes-def-N` and the text `N`. After the last chunk, one extra `Md2HTML` renders a footnote section source made of a paragraph citing every reference occurrence in document order, every footnote definition, and the link definitions those cite; only its `.footnotes-defs-div` is appended. Requirement: the assembled HTML equals one-pass `Md2HTML` of the masked text (Vitest).
6. **Threshold and chunk size.** `PREVIEW_STREAM_MIN_CHARS = 50_000` and `PREVIEW_STREAM_CHUNK_CHARS = 16_000`; a document streams when its length is greater than the threshold. Evidence: one pass of about 50 KB is about 100 ms; a 16 KB chunk measured 27-29 ms (4 KB 8-11 ms, 32 KB 52-61 ms); Preview DOM is not editable, so the edit modes' 700 KB reflow reason does not carry over. *Provisional decision (2026-11-01), reversible.* Selected by a recorded decision check (probability 0.71; 200 K threshold 0.13, 4 K chunks 0.12; both checked requirements supported).
7. **Stream loop.** As `streamRenderIR`: render a chunk to a detached holder, move its top-level nodes into the pane, run the cheap passes on the new nodes only, yield one animation frame once 12 ms of work has piled up. A generation token aborts a stream when a newer render starts, Preview is turned off, or the editor re-inits. A one-pass document uses the same code path with one chunk and goes through `morphPreviewInto`, so a host update keeps unchanged blocks' live DOM; after a stream, the morph baseline is set from the assembled unit strings (new export `setPreviewMorphBaseline(el, raws)` in `preview-morph.ts`). A host update to a streamed Preview renders all units off-DOM with yields, then applies one morph. A renderer exception in a one-pass render returns `false` from the hook so Vditor's own render runs; an exception mid-stream falls back to one Vditor render of the whole text.
8. **On-screen first (requirement 4).** Cheap passes run per chunk on new nodes: `renderImageCaptions`, `codeRender` (copy buttons), `mediaRender` when enabled. A top-level block is heavy when it matches or contains `pre > code, .language-math, [class*="language-"]`. A heavy block outside the viewport plus `PREVIEW_RENDER_MARGIN_PX = 800` gets `data-vmde-preview-pending` and is queued on a `createViewportGate(800)` (`nav/viewport-gate.ts`). On release the renderer removes the attribute, runs the native renderers in `afterRender`'s order (`highlightRender`, `mermaidRender`, `markmapRender`, `SMILESRender`, `flowchartRender`, `graphvizRender`, `wavedromRender`, `chartRender`, `mindmapRender`, `plantumlRender`, `abcRender`, `mathRender`, then `customRenders`) against `blockQueryRoot(block)`, an object whose `querySelectorAll(sel)` returns the block itself when it matches plus its matching descendants (every listed renderer reads its root only through `querySelectorAll`, checked in the Vditor sources), and dispatches the document event `PREVIEW_BLOCK_RELEASED_EVENT = 'vmde-preview-block-released'` with `detail.block`. `findBlocks` (`diagram-kit/diagram-dom.ts:113`) skips elements inside `[data-vmde-preview-pending]` (beside its `isSectionHoistHidden` filter), and `observeCustomDiagrams` adds the released block to its pending set and schedules, as it does for hoist scope changes. At stream end: ToC blocks filled as in `afterRender`, `vditor.outline.render(vditor)`, then the existing completion hook `__vmdePreviewRendered(vditor, element, renderId)` so checkbox binding and reuse commit happen once, for the whole document.
9. **Preview-first open and the deferred edit view.** In `initVditor`, `openPreviewFirst = msg.options?.defaultMode === 'preview' || reopenRememberedPreview`, for every document size (the streaming exclusion at `vditor-init.ts:597-605` and the "only remembered Preview opens after a stream" rule at `:553-555` are replaced). Construction follows the `willStream` shape (value `''`, the same `streamModeDecision` for the construction mode). In `after()`: theme, wiki renderers, `installToolbarFlow`, `runFinishInit` (with `startIncrementalSeed` deferred), `openInPreview()`; the prerender overlay is removed at the first Preview content. `sessionState.deferredEditView` holds `{ text, mode, history }` until the first switch. Leaving Preview runs `ensureEditView()` from a capture-phase click listener on the Preview control's wrapper, before Vditor's handler: a document at or below `STREAM_MIN_CHARS` builds with `vditor.setValue(text)` under `applyingExtensionUpdate`; a larger one streams through the existing `streamRenderIR`/`streamRenderSV` with `sessionState.streaming`; then EditSync invalidation, `startIncrementalSeed()`, and the history base capture. The edit view is built at most once per editor instance.
10. **Host text while Preview-only.** `handleUpdate` checks `deferredEditViewPending()` before its streaming and `getValue()` branches. A pending view adopts the revision, replaces `deferredEditView.text`, reseeds EditSync's exact text (`reseed(undefined, content)`), and re-renders Preview through `refreshVisiblePreviewAfterHostUpdate` (morph). An ordinary external update clears `history`.
11. **Checkbox Undo while Preview-only.** An accepted owned checkbox echo (the existing `previewTaskCheckboxHistory` with a matching pending request) is queued in `deferredEditView.history` as `{ before, after, renderedAfter }`. At the first switch, the edit view is built from the first queued `before` (or `text` when the queue is empty), then each entry is replayed through the existing owned-history apply path (`setHostUpdateValue` with the owned record), giving one native Undo step per toggle, as today. A document over `STREAM_MIN_CHARS` replays with the same monolithic path (known cost, recorded). *Provisional decision (2026-11-01), reversible.* Selected by a recorded decision check (probability 0.99; build-on-click contradicted "edit view not built before the switch", no-history contradicted "one Undo step").
12. **Reading position across switches.** Keep `nav/preview-scroll-preserve.ts`'s longest-common-subsequence block pairing (Task 364); no source line stamps (the vendored Lute has no source positions, and per-block lines would need a second block parser). Changes: the Preview-entry pin and the leave-Preview pin stay active until the Preview stream or the deferred edit build finishes, then for the existing `PREVIEW_PIN_MS`/`EDIT_PIN_MS`. A Preview-first open with a saved reading position restores it onto Preview top-level blocks through `resolveBlockAnchor` (`nav/block-anchor.ts`; hash, heading path, index fallbacks), when the anchor's block exists or the stream ends. *Provisional decision (2026-11-01), reversible;* covered by decision 1's check.
13. **Find (requirement 7).** The provisional Find design is confirmed: a Preview search source over the rendered Preview DOM. Text is collected from text nodes under `previewElement`, skipping `svg`, the hidden MathML copy inside KaTeX output (`.katex-mathml`), `.vditor-copy`, `.vmde-*` decorations with `aria-hidden`, hidden nodes, and code blocks of diagram languages (the engine registry list); a `\n` separator is inserted at each block-level element boundary, so a single-line query never matches across blocks, while matches may cross inline elements. Matching reuses `findMarkdownMatches`; a `FindMapper` builds DOM ranges from text-node offsets and reports visible matches. Text in pending heavy blocks that is not displayed is not searchable; matches refresh after each streamed chunk (debounced). In Preview, `openFindReplace('replace')` opens Find with the Replace row hidden, the Replace toggle is disabled, and `replace-one`/`replace-all` actions and keys do nothing. Cross-block matching: *Provisional decision (2026-11-01), reversible.* Selected by a recorded decision check (probability 0.97).
14. **Safety while the edit view is pending.** EditSync's `isSuppressed` also returns true while `deferredEditView` is set; `onHistoryBase` posts nothing; the save flush posts no `edit`. The document, dirty state and Undo history change only through host updates and checkbox echoes.

### Invariants

1. While the edit view is pending, no `edit` or `history-base` message is posted and the save flush posts nothing.
2. Chunked Preview HTML equals one-pass `Md2HTML` of the masked text; full-Preview output equals the Split pane's render of the same text and settings.
3. Split's preview pane path is unchanged (the hook returns false there).
4. Each host update while Preview-only adopts its revision and replaces the deferred text exactly once.
5. The edit view is built at most once per editor instance, only when the user leaves Preview.
6. A render failure never leaves Preview empty or half-rendered without a fallback render.

### Edge cases

Empty and whitespace-only documents; lengths 50,000 (one pass) and 50,001 (stream); footnote definitions in another chunk, repeated references, unused definitions, references without a definition; a footnote or link definition inside a fenced code block (`buildDefMap` is not fence-aware; same limitation as edit streaming, recorded); duplicate labels; lists, fences and HTML comments spanning a chunk cut (lists and fences by `chunkize`, comments by masking first); `[toc]`; a host update during a Preview stream (restart with the new text) and during a deferred edit build (`deferredHostUpdate` replay, as today); a config or theme change while Preview is shown (routed re-render); re-init or Preview off mid-stream (generation token); leaving Preview mid-stream; checkbox clicks before the stream ends (bound at stream end); WYSIWYG remembered mode with a document over 700,000 characters (session-forced to IR, as today); wiki links before page keys are known; Find opened mid-stream; outline open while streaming; a reading position saved in an edit mode and restored in Preview.

### Risks

- `runFinishInit` on an empty edit view followed by a later wholesale build: helpers that assumed a built document at install time may miss the build (the streaming path proves most handle it; step 5/6 tests and step 11 switch specs cover it).
- A streamed edit build after helpers are installed may make mutation observers do per-chunk work (O(n²) risk on the 800 KB switch); measured in step 11.
- Checkbox replay on documents over 700,000 characters is a monolithic setValue per toggle.
- Real-VS-Code timing variance (about ±15%) against the 30 KB ratios; medians of 3 are used.
